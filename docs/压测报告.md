# 压测报告

数据全部来自本机实跑，命令与结果逐条对应，未做任何美化。

## 环境

| 项 | 值 |
|---|---|
| 机器 | 本机 Windows 11（25H2, build 26200），单机自测 |
| Python | 3.12.14 |
| 服务 | uvicorn 0.54.0 + FastAPI 0.165.0，单进程单 worker |
| 索引 | 60 个切片，HashingEmbedder(dim=1024) + BM25 + RRF |
| 压测客户端 | scripts/bench.py（httpx，ThreadPoolExecutor，trust_env=False 直连） |
| 网络 | 本机回环 127.0.0.1 |

## 命令

```bash
python -m uvicorn api.main:app --host 127.0.0.1 --port 8033
python scripts/bench.py --url http://127.0.0.1:8033 --requests 300  --concurrency 8  --json reports/bench_c8.json
python scripts/bench.py --url http://127.0.0.1:8033 --requests 1000 --concurrency 32 --json reports/bench_c32.json
```

## 结果

### 并发 8，300 次请求

| 指标 | 值 |
|---|---|
| 成功率 | 100%（300/300） |
| QPS | **157.4** |
| 平均延迟 | 50.7 ms |
| P50 | 48.2 ms |
| P90 | 62.0 ms |
| **P95** | **68.9 ms** |
| P99 | 80.0 ms |
| 最大 | 85.8 ms |
| 服务端自测延迟 P50 / P95 | 4.8 ms / 23.8 ms |

### 并发 32，1000 次请求

| 指标 | 值 |
|---|---|
| 成功率 | 100%（1000/1000） |
| QPS | **148.5** |
| 平均延迟 | 213.3 ms |
| P50 | 211.8 ms |
| P90 | 229.1 ms |
| **P95** | **235.3 ms** |
| P99 | 244.8 ms |
| 最大 | 252.5 ms |
| 服务端自测延迟 P50 / P95 | 4.9 ms / 5.9 ms |

## 结论

1. **吞吐在 150 QPS 左右封顶**。并发从 8 提到 32，QPS 反而从 157 掉到 148，说明瓶颈不在检索逻辑，而在单进程 uvicorn 的事件循环 + 压测客户端线程池的争用。
2. **服务端自身很快**：服务端自测 latency_ms 的 P95 只有 5.9 ms，端到端 P95 的 235 ms 大部分是客户端并发排队和本机回环上的请求堆积。
3. **混合压测无错误**：所有请求 200，错误率 0%，说明并发下索引读取是只读安全的（RagService 里 pipeline 按 (top_k, mode) 缓存，没有写操作）。
4. 要往上提吞吐，第一选择是 `uvicorn --workers N`（多进程，每进程独立加载索引），其次是给索引加进程内缓存/向量检索换 ANN。当前 60 个切片的规模下没必要。

## 已知说明

- 压测是本机回环，不涉及真实网络 RTT，所以 P95 反映的是服务端处理能力 + 客户端调度，不代表线上 HTTP 时延。
- 数据来自 `reports/bench_c8.json`、`reports/bench_c32.json`（由 bench.py 自动写入）。
- 踩坑记录：Windows 上开着系统代理时，httpx 默认 `trust_env=True` 会通过 `urllib.request.getproxies()` 读到注册表里的代理设置，把发往 127.0.0.1 的压测请求也塞进代理，结果全部 502。bench.py 里已改为 `httpx.Client(trust_env=False)`。

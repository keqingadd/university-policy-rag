# 答辩问答准备（评委可能追问）

## Q1 为什么切片 500 字、重叠 80？
规章和办法的"条"通常 100–400 字，500 字能装下完整条款，重叠 80 字避免答案跨块被截断。参数在 `scripts/build_index.py` 可调，并用评测集验证。

## Q2 为什么 BM25 + 向量 + RRF，而不是只上向量？
政策文本有大量精确字段（10 日、5 个工作日、LPR 减 60 个基点、16000 元），纯向量对这类匹配不稳：口语化问法纯向量 Hit@1 只有 50%，混合检索靠 BM25 兜住到 83.3%。RRF 只依赖排名、不用调权重。

## Q3 查询改写具体怎么做？为什么不用大模型改写？
维护一张领域同义词表（评贫困生→家庭经济困难学生认定、国奖→国家奖学金、打工→勤工助学），查询时把命中的规范表述追加进检索文本。零训练成本、可解释、可逐条维护。大模型改写更适合下一步做 A/B，而不是一上来就依赖它。

## Q4 改写的效果怎么证明？
做了消融：同一套 6 道口语化题，无改写时 Hit@1 66.7%/Hit@5 83.3%/MRR 0.708；加改写后 100%/100%/1.00。报告在 `reports/` 下可复现。

## Q5 怎么防止大模型编造？
三层：①提示词限定只能依据资料、必须标引用；②检索不足直接返回"未检索到"；③后续加引用校验（答案里的 [n] 必须能在上下文找到）。

## Q6 政策过期了怎么办？
政策文本是抓取时点的公开版本，所以产品上要支持文档版本管理、更新时间提示和引用溯源；实际办理以最新文件为准。这一点我在 README 里也写了。

## Q7 文档是 PDF / 扫描件怎么办？
当前用 Markdown；PDF 可用 pdfplumber / PyMuPDF 提取（本项目已用来渲染 PDF 页面），扫描件需 OCR。真实场景中文档清洗往往占一半工作量。

## Q8 性能怎么样？
59 个切片上检索平均 0.3 ms，瓶颈在生成（1–3 秒）。上线会做 Top-k 限制、缓存、流式输出；接口无状态可水平扩展。

## Q9 这个项目你做了多久？最难的部分？
约 X 天（按实际写）。最难的是"用词差异"——第一版没有查询改写时，口语化问法 Hit@1 只有 66.7%，评测暴露出问题后加同义词表才解决。这件事让我意识到：RAG 的上限是检索，而检索的很多问题出在"用户和文档说的不是同一套词"。

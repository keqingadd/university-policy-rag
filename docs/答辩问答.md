# 答辩问答准备（评委可能追问）

## Q1 为什么切片是 500 字、重叠 80？
示例文档的小节普遍 200–600 字，500 字能装下完整小节；重叠 80 字防止答案跨块被截断。切片过短会丢上下文，过长会稀释相似度并增加生成成本。参数在 `scripts/build_index.py` 里可调，并用评测集验证。

## Q2 为什么用 BM25 + 向量 + RRF，而不是只上向量？
企业文档有大量精确符号（429、AES-256、9.8 万元、K8s 1.26），纯向量对这类匹配不稳定；BM25 保精确，向量保语义改写。RRF 只依赖排名、不用调两路权重，工程上最稳。评测也支持：口语化问法混合检索 Hit@5 100%，单路只有 83.3%。

## Q3 你的向量是怎么来的？为什么不用 bge？
默认用零依赖的字符 n-gram 哈希向量，保证任何电脑、无网络都能跑通全流程，方便演示和复现；真实场景通过 `RAG_EMBEDDER=api` 换成 bge-m3 等模型，重跑建索引即可。这是"可插拔"设计，不是能力上限。

## Q4 怎么防止大模型编造？
三层：①系统提示限定只能依据资料并标注引用；②检索不足时直接返回"未检索到"，不给模型发挥空间；③下一步做引用校验（答案里的 [n] 必须能在上下文找到），并用评测集统计拒答率/幻觉率。

## Q5 文档是 PDF / 扫描件怎么办？
当前支持 Markdown/TXT；PDF 和 Word 需要先转成 Markdown（pdfplumber / python-docx / OCR），转换放在 `data/docs/` 的预处理步骤。真实企业场景里文档清洗往往占一半工作量，这是下一步要补的。

## Q6 性能怎么样？
31 个切片上检索平均 0.1 ms，瓶颈在生成（一次约 1–3 秒）。上线会做 Top-k 限制、上下文截断、相同问题缓存、流式输出；接口无状态，可水平扩展。

## Q7 和直接问 ChatGPT 有什么区别？
区别在"可信"：答案限定在企业自己的文档里，带出处可核查，资料不够会承认不知道；检索和评测都可控，能持续迭代效果。

## Q8 这个项目你做了多久？最难的部分？
约 X 天（按实际写）。最难的是切片策略——第一版按段落硬切，关键词问法还行，但口语化问法经常答非所问；改成标题感知切片 + 混合检索后，口语化问法的 Hit@5 才到 100%。这件事让我意识到检索质量决定 RAG 的上限。
